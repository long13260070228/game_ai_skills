# 固定版本与证据审查

唯一模式为独立发现，`mode: independent`；技能版本 `v5.13.1-feedback`，沿用 `classification_schema: local-flow-v1`。只审查，不修改业务代码；用户范围与授权优先。旧报告继续使用原冻结技能和渲染器，不重写其发现版本。本版优化执行组织，不承诺固定提速、穷尽问题或重复运行一致。

## 默认执行与按需读取

- 范围：默认覆盖本次新增及目标仍存在的历史问题，历史单列；用户限定仅新增时从其限定。按真实功能分配未变更模块，不因代码相同自动排除。范围、输入和完成性分别记录；归因未知不当作历史或新增。
- 目标：增加有证据的独立根因，完成必要覆盖与反证；不设问题数目标，不提高等级或降低确认门槛。有效规范明确约定的文字、动画、反馈先判断行为语义，不能只按载体排除。
- 执行：1轮独立发现→原稿冻结→核证与补漏→终稿核对→一次导出。已授权的大型高覆盖审查保留关键分区双独立发现；横向补漏不能替代第二份原稿。未完必需检查继续，不以轮数或已有问题数收口。
- 协作：只在当前平台和用户授权内使用Agent，最多6个、不要求用满；配置及复用遵循当次指令和全局规则。全部约定独立原稿冻结前不交换候选。每项确定结论须具名非作者核证；明确接受单人时标作者自审，不能冒充独立核证。
- 记录：原稿、案例、来源及核证各留一份，以稳定ID引用。沿用现有sources、coverage、findings、handoffs、timings，不新增同义账本；只补变化、冲突、未决与必要覆盖。
- 反馈：默认采用下述“逐项反馈＋最终统一交付”；阶段反馈不结束审查，也不提前导出交付包。
- 交付：复用既有模板与工具，生成同源HTML、JSON、Markdown、来源清单及一个去重证据ZIP/SHA。审查不转为页面设计；不得为省交付时间跳过必要数据、链接及包检查。

## 逐项反馈与最终统一交付

- 默认同时提供两阶段结果：每项完成确认后及时在当前聊天反馈，随后继续范围内的发现、补漏及核证；全部必需工作完成后统一交付。用户明确要求只在最后汇总时从其要求，不改变发现模式 `mode: independent`。
- 首次候选交流仍须满足本轮约定的全部独立原稿屏障；联合审查中的“已确认”还须完成该项具名非作者核证。候选、作者初判及待核项不提前称确定；明确获准单人审查时标注作者自审。屏障解除后确认一项反馈一项，无须等待其余问题全部核证或最终打包；若尚在独立发现阶段，只报覆盖进度和真实阻塞，不泄露候选。
- 先将确认结果及证据保存到现有 findings/handoffs，再使用同一稳定ID简报：等级、问题、合法触发、实际与预期、已证影响及条件、关键证据定位、核证状态。局部合同与完整流程可达性分开，不将静态证明写成线上复现；阶段等级及归因仍可随新证据更正。
- 简报使用过程消息，说明继续审查，不以最终回复结束回合，不逐项询问是否继续，不为反馈放宽核证标准、提前停止覆盖或反复生成HTML/ZIP。同根只报一次，相关补证沿用原ID；新反证导致结论撤回、收窄或等级变化时及时说明并在现有 review_history 留痕，不悄然覆盖原稿。
- 阶段消息仅面向用户，不转发给尚未完成独立原稿的执行者，也不作为其他独立样本的输入；新建或接力上下文时保持隔离。用户据阶段结论提出新指令时先核对其范围和独立性影响，不自动转为业务修复。
- 最终仍由同一 JSON 派生完整报告与一个去重证据ZIP/SHA，包含确定、待核、排除及修订记录，完成原有终检和必要验收；逐项反馈不构成整轮完成或提前发布批准。不另建平行反馈账本。

入口与本轮用过的参考无需反复通读；版本或规则改变时补读受影响部分。按阶段读取：

| 分配大型任务、覆盖或交接收口 | [coverage-completion](references/coverage-completion.md)：双独立发现、条款闭合、具名核证和停止条件 |

## 1. 固定输入及边界

- 记录仓库、完整目标提交、基线提交、审查模块与允许数据源。只从固定 Git 对象读代码和资源；工作区、默认分支和后续提交不得替代目标版本。
- 提供MR链接时先按 [references/mr-intake.md](references/mr-intake.md) 解析并冻结仓库身份、差异版本及提交。本地仓库不是前置条件：已有对象只读复用，缺少时在隔离目录获取；固定版本源码可由API完整读取时也不强求本地检出。MR源分支提交通常是报告target，不能因平台称“目标分支”就倒置；具体比较口径按该协议登记。
- 从允许输入建立 `sources` 清单：ID、种类、路径、版本/修订、哈希、时间、允许用途与限制。需求截图的文字描述、纯文本抽取、转述和旧审查结论不能自动当作有效需求原文。
- 单列必须数据、可选验证数据、缺失数据及禁止使用来源。已有同版材料补读、新隔离实验、版本/范围扩张分别登记；另记“接触过但排除”，不得混同于“未访问”。
- 从原始资料独立提出候选；隔离旧报告、参考答案、既有缺陷清单及其衍生的定位、探针和结果，不接受旧条目作为派工线索。
- 不为了补证读取服务器实现、更新版本、后续 bug 或美术资料等未授权来源。缺失证明保留为缺失。
- 用户提供的原始设计/设计评审文档属于允许的候选规范来源，不能因目录名含“评审”而当作历史缺陷报告排除；若其中混有历史Bug或旧审查结论，隔离那些内容。核原文、版本、效力及与需求的兼容/冲突，不自动用设计覆盖产品规则，也不将设计当作实际部署证据。设计条款须进入覆盖账本、输入清单和证据交付包；详见review-protocol。
- 客户端可提供的数据类型为 MR、产品需求文档、客户端/服务端开发设计文档、美术资源、配表及 SVN；按实际收到的材料登记，不视为全部已提供或全部必需。Bug 列表与服务端源码不提供，不索取、不搜索替代，也不作为开始或完成客户端静态审查的门槛。各类来源的用途与版本绑定见 [references/review-protocol.md](references/review-protocol.md)。

核证前简要公布本轮实际输入及缺口、两个版本、新增Bug归因口径和严重度规则；材料自带等级不自动成为本轮标准。输入/规则变化须版本化，不能事后静默更换。

## 2. 按范围建立覆盖，准备一次

先从原始规范和固定树建立功能、条款及入口归属，即可启动分区；不等全仓解析完成。条款索引不能只来自关键词或已有findings；预期保留原文的触发、时间点、量词及例外，不能按实现改写。

两轴交叉检查：规范→实现，核独立用户结果；实现→不变量，核状态、异常/恢复、数据及消费者。功能链为入口→初始化→操作/通知→数据→反馈/退出；依赖链为协议/实际配置→分支→资源绑定→宿主。适用载体按项目选取，不强套某技术栈清单。

历史审查由目标功能与有效规范派生任务，不只看diff；历史归因须证明基线同场景、同规则已有缺陷。仅新增审查允许补读未变更依赖核因果，不扩大为独立历史审查。两种范围的未覆盖模块明确记录。

按[efficient-review](references/efficient-review.md)复用固定原件、解析及索引；缓存不是覆盖证明。每个独立结果保留同触发、同期望、同消费者的案例，复合条款分开判定，不能从父状态或证据并集推导子结果已满足。案例与状态含义见output-contract。

大型分工、关键分区双独立发现、已满足/范围排除抽查及未决收口统一按[coverage-completion](references/coverage-completion.md)执行。不得以横向扫描、只读文档或只读代码替代任一关键功能审查；已读未核、可读推导未完保留unfinished_check，不能改名缺输入。

## 3. 提出候选并主动寻找反证

逐项先固定已有方法/接口组成的完整局部边界及合法域，再记录实际行为、预期依据、根因、最小影响、流程可达性、保护措施与不确定因素。边界内必经前置不能截断；边界外有Bug的构建路径另核flow，不将其实际成功回绑为局部合法性门槛，也不任意构造模型或假设上游修复。细则见decision-rules。

- 读完整方法、调用者和异步返回路径；检查提前返回、默认值、外部刷新、生命周期及 UI/资源绑定。不要把片段缺少某逻辑等同于整个功能缺少。
- 用上游失败限制候选时，先核异常前已绑定的动作与已写入字段，沿仍可执行的动作核其消费者及完整守卫。阻断成功回调不等于阻断全部交互；缺这段推导应记 unfinished_check，不能将整个模块直接沿用同一流程阻断判定。
- 检查重复进入、冷启动与已有缓存、取消后继续、操作前后状态、空/缺字段、边界档位及时间区间。只有能从允许的代码、配置、协议、资源或运行证据推出的条件才可声称可发生；条件可行但未证明生产出现要标明。
- 核实配置真实取值及入口注册；潜在错误分支但本版配置不可达，归入未启用配置风险。
- 需求类结论必须引用有效规则。核对原始富文本的删除/修订、补充说明、版本、相互冲突；纯文本无法复验时将代码事实与规范有效性分开。
- 对表面协议差异核对序列化与模型、文档口径；没有真实响应或对端实现，不能断言对端一定失败。
- 对缺失功能，列出搜索范围、入口和反证检查。以文档描述证明预期，以调用链/配置/资源证明缺失，分别引用。
- 新增归因要对比基线行为与适用场景；文件新增不等于需求新增，复用旧实现也不等于新场景适配正确。不能仅按提交日期推定原因。

发现有证据的根因后，按efficient-review在本轮范围内检查相关同类路径，逐项证明差异；同类扫描不替代尚未覆盖的功能审查，遵守独立原稿屏障。

## 4. 分开判定事实、缺陷与来源

每项独立填写。判定边界、重叠状态及主归因选择见 [references/decision-rules.md](references/decision-rules.md)：

- `claim_scope`：选择 `local_contract`（局部合法输入下的必然违约）或 `user_flow`（完整玩家流程结果）；`local_input_basis`证明输入及调用前提合法，`flow_reachability`独立记录可达、已确认Bug阻断、未证或配置未启用。局部证据闭合可为confirmed并计Bug，不能据此宣称玩家已遭遇该结果。字段与判定详见上述参考及output-contract。
- `status`：`confirmed`（固定条件下有完整代码和规范/自身不变量证明）、`conditional`（所选claim_scope必需的前提未证；局部已闭合而纯流程未证不因此降级）、`requirement_unverified`（代码事实明确，规则有效性未核实）、`inactive_config`、`refuted`（有明确反证）、`unresolved`。
- `origin`：`new_implementation`、`new_requirement`、`migration_gap`、`historical`、`unknown`。为归因另给基线/需求证据，不与严重度或确定性混用。
- `evidence_level`：静态推导、隔离执行、真实集成/运行；标明实测了哪一部分。探针必须保留代码、输入、命令、输出、模拟对象和证明限制，不把模拟结果写成线上复现。
- `scope`：依据是否在允许边界，是否同版补读/新增实验/排除接触；越界数据不作为结论依据。
- `evidence`：证据源 ID、固定版本路径及行范围/文档段落、短引文、该证据支撑的具体断言。每条确定结论均有来源、与claim_scope对应的合法性证明、独立流程可达性判定及反证检查。

收窄影响优先于扩大猜测。未证影响不是已反证；待确认项不统称误报。相同根因合并，独立状态缺陷不因在同一文件而合并。

按 [references/severity.md](references/severity.md) 独立判定 `severity: P0/P1/P2/P3/P4`，另填 `severity_basis`。严重度、确定性、归因分别判定；待证的灾难性后果不得抬高已证局部缺陷的等级。P0/P1须逐项核证严重后果、合法触发、影响范围与恢复限制及对应流程证据；未实测本身不设等级上限，被阻断局部项也不继承阻断者等级。正常恢复须有实际实现提供的用户操作/自动恢复完整链，可静态核证；改对端编码或开发修复不算用户绕过。真实严重缺陷仍必须报告，不得为满足验收而降级或隐藏。

冻结前按覆盖收口参考核证全部confirmed所声称的窄断言：默认逐项由非作者具名复核，先寻找足以推翻结论的反证，再独立核正面证明，不能只认可作者摘要；用户明确接受单人审查时可单列作者自审，不能声称完成了非作者核证。不只复核严重项或争议项；另优先读未被现有结论覆盖的原文条款及异步时序；大范围可由独立横向职责先从原始资料扫描，再与功能分区对账。对待核理由本身举证，不能将已提供但未找到的规则写成缺输入。所有跨职责移交须有具名接收者、判定和证据，不能将“已转交”当已核。

## 5. 交付并校验

按 [references/output-contract.md](references/output-contract.md) 写 JSON，以其为单一事实源。运行：

```bash
python3 /ABSOLUTE/SKILL/DIRECTORY/scripts/report.py /ABSOLUTE/review.json --out /ABSOLUTE/OUTPUT_DIRECTORY
```

将命令中的技能目录替换为本次实际读取的技能绝对目录。版本、非空模块、确定/待确认、P0～P4及新增/历史/旧代码×新配置的互斥统计与筛选，统一按output-contract执行，由同一JSON派生，不手填第二套数字。版本区逐行显示冻结分支和完整SHA，不查询实时分支替代。

最终交付先整理review.json、data-sources.md及必要证据，再运行一次：

```bash
python3 /ABSOLUTE/SKILL/DIRECTORY/scripts/bundle.py /ABSOLUTE/OUTPUT_DIRECTORY --zip /ABSOLUTE/OUTSIDE_DIRECTORY/evidence.zip --finalize
```

该命令同源生成Markdown、本地/离线HTML、一个去重证据ZIP及SHA-256；report.py用于必要预览，不必先重复渲染。已冻结成果重打包时按delivery-maintenance保留其冻结渲染器及原Markdown，不擅自重判或迁移。

交付四项报告：index.html、review.json、review.md、data-sources.md。唯一推荐阅读入口为index.html，顶部结论/统计、证据包下载、问题总览与详情；完整输入、分级标准、来源、覆盖及审计后置折叠。包信息、去重、包内入口及链接检查由现有bundle复用处理，详见delivery-maintenance；默认不另加阅读包。

终稿核对数量、等级、条件、归因、来源及跨格式一致性；复用本轮已具名闭合且证据未变的核查，只补冲突、变更、未决及必要覆盖。明确范围变化、缺口、静态/隔离/真实运行与网页视觉验收的实际边界。脚本通过不证明语义正确，文件存在不证明审查完成；不得把完整交付说成完整工程或无缺陷保证。

## 6. 独立性与结果冻结

冻结本次技能版本及输入清单。使用未接触旧问题或参考答案的上下文，只读允许的原始资料和技能；已有上下文接触过答案时，不能靠“不读答案”恢复独立性。独立发现上下文避免读取会附带历史结论的会话或Agent清单；需要复用池核查时，由非发现调度者先核查并仅传达去除结论的可用配置。意外接触要记录并标为受污染。隔离旧结论衍生的定向探针，不排除目标版本仓库本来就有的测试。

对自己独立提出的候选可反向核证和自审，完成后冻结结果。若用户另行要求与历史结果比较，由结果冻结后的独立评估步骤处理；不向发现阶段提供参考标题、数量、定位、分级或旧探针，不将比对后补证倒填独立发现。计数分别列确定项、待核项、配置未启用项及已排除候选。确定项按claim_scope互斥拆分，同根唯一；被阻断与可达未证是确定项内部的流程子计数，不与总数相加。不能把记录总数称作确定 Bug 总数。

只将通用过程缺口补入技能，禁止加入项目名、特定标识符、答案数量、具体问题、预期结论或定向搜索语句。保留修订前后快照及差距，复验仍不提供参考答案。经验校准只证明该输入上的表现，不推定对其他项目同样覆盖。

若无基线，明确写未知及原因，仍可审查目标事实，主归因保留 unknown。多仓库逐一固定版本，不用一个提交代表所有依赖；Git、SVN 与文档修订分别绑定。独立复验需另隔离上下文；在同一上下文继续补核只能称继续审查，不能证明新样本表现或修订的因果收益。
